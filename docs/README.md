# 1단계 요구사항 - 웹에서 로그인하기

## 미션 배경

예약 서비스는 지금까지 이름을 입력받아 사용자를 구분했다. 이제 웹 사용자는 로그인한 뒤 예약 서비스를 사용해야 한다.

이름 입력 방식은 작은 서비스에서는 단순하고 편리했지만, 사용자가 늘어나면 한계가 드러난다. 다른 사람의 이름을 입력할 수도 있고, 같은 이름을 가진 사용자가 있을 수도 있다. 예약을 만든 사람이 누구인지 신뢰하기 어렵다.

1단계에서는 이름 입력 기반 예약 흐름을 로그인 사용자 기반 예약 흐름으로 바꾼다.

## 목표
- [ ] 사용자가 웹에서 로그인할 수 있다.
- [ ] 로그인한 사용자를 기준으로 예약을 생성한다.
- [ ] 로그인한 사용자를 기준으로 예약을 조회한다.
- [ ] 로그인하지 않은 사용자는 인증이 필요한 기능을 사용할 수 없다.
- [ ] 인증 로직이 컨트롤러마다 반복되지 않게 한다.

## 요구사항

### 로그인
- [ ] 사용자는 로그인할 수 있다.
  - 로그인 기능
- [ ] 로그인에 성공하면 이후 요청에서 같은 사용자를 식별할 수 있어야 한다.
  - 세션
  - 토큰
- [ ] 로그인에 실패하면 적절한 응답을 반환한다.
  - 로그인 실패 이유
    - 존재하지 않는 ID
    - 패스워드 불일치

### 예약 생성
- [ ] 로그인한 사용자는 예약을 생성할 수 있다.
  - 사용자 예약 생성 기능
- [ ] 예약 생성 시 요청으로 받은 이름이 아니라 로그인한 사용자를 기준으로 예약을 만든다.
  - 로그인한 사용자 정보로 예약의 식별자를 생성한다.
  - 사용자 1 : 예약 N
- [ ] 로그인하지 않은 사용자는 예약을 생성할 수 없다.
  - 예약 생성 기능은 인증이 필요하다.

### 예약 조회
- [ ] 로그인한 사용자는 자신의 예약을 조회할 수 있다.
  - 이름 -> 사용자 인증 정보
- [ ] 로그인하지 않은 사용자는 인증이 필요한 예약 조회 기능을 사용할 수 없다.
  - 예약 조회 기능은 인증이 필요하다.

### 인증 공통 처리
- [ ] 로그인 여부 확인 로직을 컨트롤러마다 반복하지 않는다.
  - 세션 or 토큰 검증
  - Interceptor?
- [ ] 인증이 필요한 API와 필요하지 않은 API를 구분한다.
  - 인증 필요 O
    - 예약 생성
    - 예약 조회
  - 인증 필요 X
    - 로그인
    - 현재의 요구사항으로는 나머지 모든 기능
- [ ] 인증 실패 시 일관된 응답을 반환한다.
  - 401 Unauthorized
  - message
    - 아래 두 가지 선택지중 선택이 필요해보인다.
    - 잘못된 정보입니다. 다시 시도해주세요.
    - 존재하지 않는 ID입니다. 패스워드가 일치하지 않습니다.

## 구현 조건
- [ ] Spring Security를 사용하지 않는다.
- [ ] 세션 또는 직접 구현한 인증 흐름을 사용할 수 있다.
- [ ] 인증에 필요한 공통 처리는 Interceptor, ArgumentResolver 등 적절한 도구를 사용해 분리한다.
- [ ] 컨트롤러는 가능한 한 로그인 사용자 정보를 직접 꺼내지 않는다.

## 구현을 하며 선택해야하는 사항

1단계의 핵심 선택은 “웹 로그인 상태를 어떻게 유지하고, 그 정보를 애플리케이션 코드에 어떻게 전달할 것인가”다. 기능 요구사항은 같아도 구현 선택은 달라질 수 있다.

다음을 직접 선택한다.
- [x] 로그인 상태 유지 방식
  - [x] 예: 세션을 사용할 것인가, 직접 만든 토큰 흐름을 사용할 것인가.
    - [x] 세션, 토큰이 무엇인가
      - 인증(요청한 사용자가 본인이 맞는가)한 사용자가 또 요청을 했을 때 식별하기 위한 데이터
      - 세션은 식별자와 인증한 사용자 정보를 서버측에서 저장하고 관리한다.
        - 사이즈가 작고, 민감한 정보를 서버에서 관리해서 안전하게 다룰 수 있다.
        - WAS가 여러 개일 경우 세션 정보를 공유하는 비용, 사용자 정보를 관리해야 하는 비용이 있다.
      - 토큰은 사용자가 저장하고 관리한다.
        - 토큰은 세션에 비해서 사이즈가 크다.
        - 페이로드에 민감한 정보를 담는 것에 주의할 필요가 있다.
        - 서버의 수평적 확장에 좋다.
    - [x] 나의 선택과 근거
      - 방탈출은 인증이 필요한 기능이 많은 편이라고 생각한다.
      - 민감 정보가 크게 없는 편이라고 생각한다.
      - 하루에 예약할 수 있는 리소스가 제한적이다.
      - 조회는 많이 할 수 있지만 cachable, 예약 생성에 대한 요청은 제한적이다.
      - 관리할 정보에 대한 데이터 크기가 작다고 생각하고, 민감 정보는 크게 없다 생각해서 고민이 된다.
      - **세션을 선택, 근거는 예약 생성 정보의 규모가 크지 않을 것으로 예상되기 때문이다.**
      - 굳이 세션정보를 RDB에 저장할 필요가 있을까?
        - 저장할 정보
          - 세션ID
          - 사용자이름
          - 전화번호
          - 로그인 시간
        - 지금은 세션ID와 사용자 이름이니깐 인메모리로 진행해보자.
- [x] 인증이 필요한 API를 구분하는 방식
  - [x] 예: 경로 패턴으로 구분할 것인가, 어노테이션이나 별도 정책으로 표현할 것인가.
    - [x] 경로 패턴은 이해가 가는데, 어노테이션 or 별도 정책은 어떤 방법인지 상상이 안간다.
    - 어노테이션 선택, API 수가 얼마 안되고, 미션의 형태라서 특정 API만 적용하고싶기 때문이다.
- [x] 인증 공통 처리 위치
  - [x] 예: Interceptor에서 요청을 막을 것인가, ArgumentResolver에서 사용자 정보를 꺼낼 것인가, 두 도구를 함께 사용할 것인가.
    - [x] Interceptor, ArgumentResolver의 코드 레벨의 이해를 높이기
    - Interceptor만 우선 적용한다. 그 이유는 컨트롤러에서 세션을 직접 꺼내 쓰는 불편함을 몸소 겪어본 후, 이를 리팩토링하는 과정에서 ArgumentResolver의 존재 가치를 체감해보고싶기 때문이다.
- [x] 컨트롤러에 로그인 사용자 정보를 전달하는 방식
  - [x] 예: 세션을 직접 조회할 것인가, 별도 LoginMember 같은 객체를 받을 것인가.
    - [x] 세션을 직접 조회할 시 장단점이 무엇일까?
      - 추상화가 없어서 단순하다.
      - 컨트롤러가 HTTP 요청의 흐름 제어 외에 세션 검증, 데이터 추출 등 인프라 기술 처리 책임이 늘어난다.
      - 보일러플레이트 코드 반복된다.
      - 순수 자바 객체로 단위테스트하기 어렵다.
    - [x] 별도 LoginMember를 사용하면 장단점이 무엇일까?
      - 관심사 분리하여 컨트롤러의 책임 고수
      - 낮은 결합도 -> 테스트 용이성
      - 추상화 구현하는 비용
- [x] 인증 실패 응답 방식
  - [x] 예: 어떤 상태 코드와 에러 메시지를 사용할 것인가.
    - [x] 401 Unauthorized
    - [x] message
      - [x] 아래 두 가지 선택지중 선택이 필요해보인다.
      - [x] 1. 잘못된 정보입니다. 다시 시도해주세요.
      - [ ] 2. 존재하지 않는 ID입니다. 패스워드가 일치하지 않습니다.
      -  1번 선택, 해커의 공격에 좀 더 안전하기 때문에

## 생각해 볼 점
- [ ] 로그인 상태는 어디에 저장할 것인가?
- [ ] 요청마다 사용자를 어떻게 확인할 것인가?
- [ ] 컨트롤러가 세션이나 요청 헤더를 직접 다루는 것이 적절한가?
- [ ] 인증 실패와 잘못된 요청은 어떻게 구분할 것인가?
- [ ] 기존 이름 입력 필드는 어디까지 제거하거나 대체할 수 있는가?

## 완료 기준
- [ ] 로그인한 사용자를 기준으로 예약을 생성한다.
- [ ] 로그인하지 않은 요청은 인증이 필요한 기능을 사용할 수 없다.
- [ ] 인증 로직이 여러 컨트롤러에 중복되어 있지 않다.
- [ ] 인증 실패 상황을 테스트했다.
